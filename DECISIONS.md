# Decisions log

Append-only record of choices made during work where the owner might plausibly have chosen differently. Newest at the bottom.

## Modernization (started at fc3edd6)

- **Plan file**: `MODERNIZATION.md` is the plan. Re-read at the start of each phase.
- **Primary goal restated by owner**: animate as many thumbnails on screen at once as possible without overloading the machine. Consequence: the video cap is not lowered as a fixed number. It becomes an adaptive budget driven by measured decoder load (dropped frames, long tasks), and the work prioritizes making each playing thumbnail cheaper (pause offscreen, proxies, native decoders). Phase 1 item 10 and Phase 3 item 3 updated accordingly.
- **Canvas grid**: removed entirely (owner: "failed experiment"). Deletes canvas-grid.js, the `useCanvasGrid` key, the Ctrl+Shift+Alt+G toggle, and all `window.CG` branches.
- **Bundler**: esbuild. Alternative was Vite; rejected because the renderer has no HMR-friendly component model and esbuild needs almost no config.
- **Type checking**: JSDoc + `tsc --checkJs`, not a TypeScript migration. Alternative rejected for churn on ~60k lines.
- **Perf profiles (low/medium/high)**: kept as a user setting, but they now scale the adaptive budget's ceiling rather than hardcoding media counts. Alternative was removing the setting; rejected because it removes functionality.
- **Plugin sandboxing**: Phase 6 moves plugin execution into a `vm` context with the explicit `plugin-api` surface. Built-ins are updated to match. Alternative (utility process) deferred as heavier than needed.
- **Prettier**: not adopted. Reformatting 60k lines would make every later diff unreviewable. ESLint + EditorConfig only; formatting rules stay as the codebase has them (4-space indent, single quotes).
- **Electron upgrade**: Phase 6, one major at a time, after the smoke test exists.
- **Background mode (owner, mid-task)**: the app must be safe to leave open behind a game. Consequences: remove `disable-renderer-backgrounding` and `disable-background-timer-throttling` (they exist precisely to keep the app burning CPU when hidden); pause every grid video and animated image when the window is blurred, minimized, or occluded; suspend prefetch, hashing, CLIP, and thumbnail generation while hidden; idle-tear-down worker pools. Added as a cross-cutting requirement in MODERNIZATION.md (section 3, "Background mode"). The existing "pause on window blur" setting becomes always-on for playback; the setting is kept to control whether playback *resumes* automatically on focus.
- **Phase 0 scope**: the linter found three real bugs (`error` undeclared at renderer.js:12451, `isAnimatedGif` undefined in main.js `resolve-file-paths`, both ReferenceErrors at runtime; `setImmediate` in renderer was guarded and only needed a global declaration). Fixed them in Phase 0 so the lint gate is green from the first commit, instead of waiting for Phase 1.
- **Fixtures**: `scripts/make-fixtures.js` generates a 1,500-image / 150-video / 60-animated reference folder into the session scratchpad for perf checks. Not committed as data; the script is.

## Phase 2 (main process never blocks)

- **Native addon made asynchronous with napi-rs `AsyncTask`** rather than calling the sync exports from Piscina workers. Same outcome for the main thread, no extra JS worker boundary or data copies, and rayon parallelism inside the task is unchanged. The ten heavy exports keep the same JS names (now returning promises) and the sync versions stay exported as `*Sync` for tests and tiny inputs. Verified: `hashFiles([])` returns a Promise.
- **Thumbnail cache switched to WebP** (lossy q82, alpha kept) via the `webp` crate (libwebp) in Rust and `sharp().webp()` in the worker fallback. Alternative was JPEG (built into the `image` crate, no new dependency) but it drops alpha; lossless WebP via `image` would only be ~30% smaller than PNG. Old `.png` entries are not migrated; they are never looked up again and age out through eviction, which now also runs every 15 minutes during a session instead of only at startup.
- **Scan ids are owned by the renderer.** The old main-generated id was returned from the invoke, which only resolves after the whole scan, so every chunk arrived before the renderer knew the id and stale-chunk filtering never applied. The renderer now generates the id, passes it in options, filters strictly, and can cancel through the new `cancel-scan` IPC. Cancellation is checkpoint-based: a native call already running completes but its chunks are dropped.
- **chokidar depth 10 → 1.** Deeper events only ever invalidated cached listings of nested subfolders; depth 1 keeps that for direct subfolders and avoids walking whole libraries on every navigation. `$RECYCLE.BIN`, `System Volume Information` and `node_modules` are ignored. Watcher batches are now one IPC message; preload fans them out so the renderer handler is unchanged.
- **Worker pools idle to zero threads** (Piscina `minThreads: 0` with 30-60 s `idleTimeout`) and the hash pool is created on first use. Startup RSS of the main process went from ~241 MB to ~121 MB.
- **`siblingTags` prefix match is now a case-sensitive index range** (`>= prefix AND < prefix + U+FFFF`) instead of `LIKE`. Paths are normalized before storage in this app, so the case-insensitive LIKE was only ever masking inconsistent input; the range scan uses the index.
- **auto-hash on folder load** is deferred to an idle callback after render, hashed in chunks of 64 in main, and superseded by the next navigation on both sides.

## Phase 3 (renderer loading, playback, background mode)

- **Order change**: canvas-grid removal moved from Phase 5 to the start of Phase 3 because every grid change in Phase 3 would otherwise have had to preserve its branches. Pure deletion, committed on its own.
- **Adaptive playback budget** lives in its own file (`playback-budget.js`) with an injected host so it is unit-tested (8 tests) without a DOM. Signals: decoder dropped-frame ratio from `getVideoPlaybackQuality()` (always counts) and main-thread stalls from a rAF loop that only runs while something plays (counts only when the playing set is at the limit and not scrolling, because stalls below the limit come from loading or layout and pausing videos would not fix them). Shrinks to 75% of the playing count on overload, grows 15% after 3 healthy seconds, floor 4, ceiling = profile `MAX_VIDEOS`. The learned limit is remembered in `localStorage.playbackBudgetHint` so the next session starts where the last one settled.
- **Forced main-process GC after every cleanup removed.** `scheduleGC()` asked main for a full `global.gc()` one second after every media cleanup. That is a main-thread pause by design, and it also collected Playwright's evaluate handles in the harness ("Resulting promise was garbage collected"). Only the minimize path still requests one explicit GC.
- **Idle cleanup loop gated on a dirty flag.** `startPeriodicCleanup` ran a full cleanup/retry/proactive-load pass every 200 ms forever (unless minimized). It now skips the pass when nothing has changed and no retries are pending; scroll, observer entries and media creation set the flag.
- **Blur/focus**: the blur handler still pauses directly (plus GIF overlays); focus no longer plays every video but asks the budget, so the resumed set respects the limit. `pauseOnBlur` keeps its meaning (an explicit "keep playing while unfocused" choice is honoured); hidden/occluded/minimized always pauses via `visibilitychange`. Harness note: Playwright emulates page focus, so the harness simulates blur/focus by dispatching the DOM events; the OS path was verified by hand earlier in Phase 1 logs (blur pauses).
- **Harness**: `--cpuprofile` records the first scroll trial through CDP; `scripts/cpuprofile-top.js` summarizes self time by file and function.
- **Zoom-50 CPU profile (scripts/perf-smoke.js --cpuprofile)** found two main-thread hot spots in a 5 s scroll: `convertToBlob` + `createImageBitmap` + `createObjectURL` (~780 ms) from building a JPEG "freeze frame" for every animated image as it loaded, and `getBoundingClientRect` (330 ms) from a forced layout per media element created. Freeze overlays are now built only the first time a card must freeze (lightbox, blur, hidden) and drawn onto a `<canvas>` instead of encoded to a blob; the More-Like-This overlay does the same, which also closes the blob-URL leak noted in the review. Card sizes come from the layout array (`getCardSizeFast`) and `isCardInPreloadZone` compares content coordinates. Result at zoom 50 on mixed-2000: frames over 33 ms per trial 33-39 → 22-25, p95 55-69 ms → 35-42 ms; zoom 100 unchanged at 0 and 14 ms.
- **First-load mystery solved (Phase 3d).** On a profile with no saved tabs, startup navigated to the remembered folder, then `loadTabs()` created a pathless "Home" tab whose `switchToTab` wiped the grid, and `initTabRestoration` re-scanned the folder over IPC and navigated again. The first tab now takes the already-loaded folder, `switchToTab` returns early when the grid already shows the tab's folder (this also removes the duplicate navigation for restored tabs), and the restoration step no longer re-scans. In-page time to first cards on a fresh profile: ~1,350 ms → 319 ms, one scan and one navigation instead of two. The harness now reports first render from the page's own clock (`timeToFirstCardsMs`) and keeps its old wall-clock figure as `timeToFirstCardsHarnessMs`; the earlier ~1.2 s readings were mostly harness round trips plus this double load.
- **Memory**: `_lbPaletteCache` (64), `_normalizeCache` (5,000) and `_shownToastKeys` (200) are bounded. `tabDomCache` and `_previewStripCache`, listed as dead by the review, are in use (tab snapshots, hover strips) and were left alone. `currentEmbeddings` is cleared on folder change already.

## Navigation state stability (owner: "navigating to a tab/folder instead opens the previous one, or fails to load, or forgets what to go back to")

The smoke test ran one action at a time; the symptoms only appear when actions overlap. `scripts/nav-stress.js` drives rapid clicks, double back presses, tab switches and closes while a 2,000-file folder is still scanning, reloads mid-load and invalid paths, and after each checks the same invariants (nothing busy or queued, grid = active tab = breadcrumb, counts match the disk, the history entry under the index is the folder on screen, no tab's cache holds another folder). It found and now guards against:

- **"The previous folder opens"**: when a grid image or video finished loading, its dimensions were written back with `updateInMemoryFolderCaches(currentFolderPath, currentItems)`. During a navigation `currentFolderPath` already names the new folder while `currentItems` is still the old list, so a late load event from the old grid filed the old folder's items under the new folder's path; the next visit to that folder was a cache hit on the wrong content. Reproduced deterministically with ten alternating clicks. `currentItems` now carries the folder it came from (`_currentItemsFolder`) and the write-back only happens when the two agree.
- **Completion-time writes keyed to whatever tab was active.** The tab content cache, the tab's path and the tab's history were all written with `activeTabId` at the moment a load finished. Switching tabs while a folder scanned handed the new tab the old tab's content and history entry. Every navigation now captures its tab at the start; the cache is only written for the tab whose path is that folder; history is added to the originating tab.
- **Loads that outlive their tab.** If the tab changed while its folder loaded, the items are cached for that tab (so returning to it is instant), its path and history are updated, and nothing on screen changes (`tab-changed`). The check runs after the last yield before rendering; an earlier version checked once and a tab switch between the check and the render still painted the stale grid (seen as a closed tab's 2,000 items appearing on the surviving tab).
- **Queued navigations crossing tabs.** A navigation queued behind a busy one ran against whichever tab was active when the queue drained. The queue entry remembers its tab and is dropped if the user has moved on; the deferred navigation inside `switchToTab` and `createTab` checks the same. `createTab` also navigated twice (once from `switchToTab`, once itself), so the first scan was always cancelled.
- **Back/forward moved the index first.** The index moved before the navigation ran; a cancelled, dropped or failed navigation left it pointing at a folder the user never reached, and the next press went somewhere unexpected. The index now moves when the navigation succeeds, with the step computed from where the in-flight or queued press will land, so two quick presses go two steps back (verified: back,back 30 ms apart; three presses in one tick).
- **Cancelled scans resolved as empty folders.** The stream's completion chunk with `cancelled: true` was treated as success: the grid rendered nothing and the empty list was cached. It is now a `scan-cancelled` rejection like the renderer-side abort.
- **Safety net**: a 90 s watchdog releases `_navBusy` if a navigation never settles, so one stuck load cannot wedge every later click. The tab's path is restored on cancellation and error from the value it had before the navigation (not from `currentFolderPath`, which can belong to another tab).

Harness lesson: the first version of the stress test polled "not busy and nothing queued" and could sample the gap between two scheduled clicks, then report a mid-navigation state as corruption. It now waits out each burst's timers and requires two consecutive idle polls. Which rapid clicks complete before the next arrives is timing-dependent (a cached folder loads in ~15 ms), so back/forward expectations are derived from the history the tab actually recorded rather than assumed. Four consecutive runs pass 29/29; `nav-smoke.js` still passes 20/20; unit tests 808/808. One later run failed S6 (switch back to the first tab 10 ms after creating a tab on a 2,000-file folder) and two reruns passed; the failing run's detail was not captured, so it stays an open flake to catch with the log the test now prints.

## Many videos on screen (owner: "enough videos on screen makes all of them lag/stutter even with barely any system resources")

Measured on a copy of the real profile's settings (zoom 50, high profile, "Maximum" thumbnails; AI scan, auto-hash and the saved tabs off so one variable moves at a time) on the owner's `7 Gifs` folder: 299 videos (720p-1080p, many at 60 fps, one 2900×2116) plus 69 animated GIFs totalling 1.4 GB (up to 90 MB each). `--keep-settings` with an explicit folder now injects the folder from an init script, because the app's own deferred writes (remembered folder, saved tabs) overwrote values set on the first page before the reload; earlier "real profile" runs that passed a folder had silently measured the previous one.

Three separate causes, each fixed and measured on its own:

- **Decoder saturation (videos).** 69 original files on screen: 12 playing with 11.5% dropped frames right after load, and the adaptive budget settling at 29. The grid now plays a small H.264 rendition of any video whose long edge exceeds the proxy size (default 480 px, at most 30 fps, no audio, the first 2 minutes; all three are settings), made by ffmpeg in the thumbnail worker pool the first time such a video is shown and cached in `video-proxies/` under its own eviction limit (4 GB default). The card plays the original until the proxy exists, then swaps source keeping position and play state; the swap waits for the original's first `canplay` so the audio-track check still sees the original. The lightbox always plays the original. Encoding is bounded (two at a time, newest request first, `-threads 2`, queued requests cancelled when the card scrolls away, half-written files swept at startup) so a page full of new videos does not turn the machine into an encoder. libx264 is required (libopenh264 accepted); without one the feature is off. After 20 s at rest: 49 playing at 0.7% drops instead of 29 (both reach all 69 after 150 s on this machine; the proxies' gain is the first minute and weaker GPUs).
- **Main-thread stalls during load and scroll (video elements).** With proxies in place the folder still loaded with 1.2-1.5 s of long tasks and scrolled at p95 118 ms with 0.6-0.8 s tasks. A CPU profile put 93% of the time in native code; a Chrome trace (`--trace`, new) showed two 777 ms full GCs inside a 7 s scroll. A `<video>` element starts a media pipeline when created and its teardown lands in the next full GC; the grid created and destroyed dozens per scroll (1,000 px preload buffer, cards recycled as they left the window). Now: while the grid scrolls, video cards get their poster frame as an `<img>` and nothing else; once it settles, poster cards in and near the viewport get their `<video>`, closest to the centre first, two per frame; `destroyVideoElement` parks elements while scrolling instead of clearing `src` and calling `load()`, and releases them three per frame after the settle. Folder loads take the same queue, which spread the initial burst (load long tasks 1,472 → 109 ms). The seek to 0 before teardown was removed (it decoded a frame for an element about to be released).
- **Image-cache stalls (GIFs).** The remaining 0.3-1 s pauses were still full GCs, but the JS heap was 20 MB and a forced GC after creating and destroying 40 videos or 200 images took 30 ms, so finalization was not the cost. The trace inside the pause showed `MemoryCache::evict` and `ParkableImageImpl::Unpark` (up to 339 ms each): animated GIFs in the grid were `<img>` elements of the original files, so 60-90 MB resources sat in Blink's image cache, decoded in full, parked to disk when off screen and read back on the main thread when evicted. Two fixes: `disable-features=ParkableImagesToDisk` (unpark 339 → 20 ms; in-memory compression stays), and GIFs or animated WebPs over 1.5 MB (or larger than the proxy edge when the size is unknown) play as the same H.264 proxies videos get: a first-frame thumbnail from the image pipeline immediately, the proxy through the attach queue when ffmpeg has made it, the animated original as an `<img>` if it cannot be made. Small GIFs stay `<img>` and keep their exact frame timing. Proxied GIF cards lose the GIF-specific progress bar and get video semantics (hover scrub, duration chip from the proxy's length, no dimension write-back from the scaled proxy).

Result on that folder, proxies cached, two scroll trials: scroll p95 14 ms (was 97-139), 4 frames over 33 ms (was 22-32), none over 100 ms (was 15-19), no long tasks (was 1.0-1.6 s per trial), largest GC 6 ms (was 300-1,054 ms); 82 videos and GIF proxies playing at 0.15% dropped frames with 4% CPU; renderer 660 MB (was 1.2-1.4 GB); hover p95 14 ms with no long tasks. Open: one 240 ms long task remains in the first load of this folder, and the proxy cache in the real profile already held 590 files from an earlier experiment (different keys; they age out through eviction).

**Follow-up (owner: "only videos in the centre ~50% autoplay, or it takes >10 s").** The playback budget started from the limit it had learned before proxies existed (13 on the owner's profile) and raised it by 15% every 3 healthy seconds, so a screen of 80 videos took over 30 s to fill, nearest-to-centre first; worse, the dropped frames of videos that had just started (first frames of a fresh pipeline, proxy swaps, posters still decoding) counted as decoder overload and shrank the limit further right after load (13 → 9 → 6 measured). Changes: (1) slow start: a remembered limit is only a starting point, and while every sample is healthy the limit doubles each sample until the first overload, after which growth is additive as before; (2) a sample taken right after the playing set changed is not evidence (those videos' first frames are expected drops), and neither is one taken while the grid is busy (navigating, scrolling, attaching or releasing videos, or within 2.5 s of the last such activity); (3) probing never starts below 32. Measured from a hint of 13 on the GIF folder: 32 playing at load, 64 at 5 s, all 82 at 7 s, zero drops at rest; previously 15 playing after 8 s. If the machine cannot sustain the probe, the next two samples shrink it (0.75 × playing) and growth turns conservative. Unit test added (10 in the budget suite).

**Follow-up (owner: "still stutters with too many on screen, barely any system resources used").** Measured on a 2560×1440 window (200 cards): with 129-200 videos playing the decoders produced ~1,500-2,600 frames per second in total, so each 30 fps proxy got 8-9 fps, media clocks advanced at 45% of real time, and almost nothing was reported as dropped: a decoder that cannot keep up stalls the clock instead of dropping frames, which is exactly the stutter the eye sees while CPU and GPU sit idle. A steady-state trace put the work on one thread each: hardware (D3D11) decode submissions serialized on the GPU process main thread and software fallbacks on the renderer's single media thread; the GPU (RTX 5080) was 4% busy. 24 fps proxies settled at the same count as 30 fps (106 both), so the cost is per stream, not per frame; the proxy frame rate is now a setting (15-30, default 30, 30 keeps the old cache key) for machines where decode time rather than stream count is the limit, and the harness got `--window WxH`, a per-video presentation-timing stutter probe and `--trace-phase steady`.

Budget changes, each with a unit test: (1) media-clock underrun is a third overload signal (currentTime advance under 90% of wall time across the playing set); (2) growth needs a stricter bar than "not overloaded" (drops under 2% and clocks at 97%+), between the two bars the limit holds, which stopped the 53↔71 oscillation at 20% drops; (3) an overload must persist for two consecutive samples (start-up drops of freshly started videos outlast one); (4) the level that overloaded is remembered as a soft ceiling (the last healthy level, or 85% of the broken one) for 60 s, doubling the hold each time the same level breaks again, so the budget stops probing back into stutter every few seconds; (5) main-thread stalls count when playing reaches the number of candidates, not only the limit. Result on the large window, 90 s at rest: 106 playing at 29 fps each (p50), clocks at 98%, 0.5% dropped, one brief probe above the ceiling per hold period instead of a stutter episode every ~15 s.

## WebCodecs playback engine (owner: "this is a band-aid; any way around Chromium's limit? Engine switch for the playback perhaps?")

Chromium's limit is per `<video>` element: a demuxer, a renderer and per-vsync compositor callbacks on single threads, plus every hardware decode submitted through the GPU process's one main thread. Two experiments fixed the direction before building. First, 60 and then 180 copies of a 1080p stream carrying a 4×4 grid of 16 thumbnails played at a full 30 fps with 2% GPU (112 streams at once), proving the cost is per stream, not per pixel or per frame. Composite tiles (option 1) would have multiplied capacity by 16 with the existing `<video>` path; the owner chose option 2, a WebCodecs engine with its own presentation, which was expected to gain two to four times. It gained more than that, for a reason the experiment could not have predicted: Chromium's *software* WebCodecs decoders scale across CPU threads, while its hardware path does not.

Design: [mp4-demux.js](mp4-demux.js) reads the proxy's sample table (avcC description, sync samples, composition offsets, edit list), tested on a tiny fixture; [webcodecs-worker.js](webcodecs-worker.js) demuxes, decodes with `VideoDecoder` and paints onto `OffscreenCanvas`es from one `requestAnimationFrame` loop per worker (four workers), keeping six frames ahead per playing player, looping with monotonic timestamps, seeking from the keyframe at or before the target, and counting a frame as dropped when a newer one was also due; [webcodecs-player.js](webcodecs-player.js) creates a `<canvas class="media-thumbnail wc-video">` per card, transfers control to a worker, and gives the canvas a `<video>` facade (play/pause/paused, currentTime with seek, duration, readyState, videoWidth/Height, getVideoPlaybackQuality, loadedmetadata/timeupdate events), so the playback budget, the hover scrubber, the blow-up overlay and teardown treat it as a video; unit tests cover the facade. In the grid, `isVideoLike()`/`getCardVideo()` replace the `tagName === 'VIDEO'` and `querySelector('video')` checks. With the engine on, a video card never builds a `<video>` pipeline: it shows its poster, asks for the proxy (every video gets one, whatever its size), and gets a player through the attach queue; the original `<video>` is only the fallback when no proxy can be made or the engine fails on a file. Proxied GIFs take the same path. The lightbox, compare and More-Like-This overlays keep their own `<video>` elements of the originals.

Two findings during bring-up: (1) a paused player must not keep its decoder: with 200 configured hardware decoders the few that played got 14 fps and the GPU process held a gigabyte of picture buffers, so a paused player closes its decoder after 300 ms and reopens it on play from the keyframe before its position; (2) hardware decoding through WebCodecs is *worse* than `<video>` on this machine (20 playing at 30% drops), software decoding plays all 200 cards of a 2560×1440 window at 30 fps with 0.009% dropped frames and 12% total CPU. Software is therefore the default (`webcodecsDecoder` setting; hardware and no-preference remain selectable). A stats report sent between a seek and its first presented frame used to overwrite the facade's clock with the old position; seeks now carry a sequence number the worker echoes only once the seek landed. The facade interpolates `currentTime` between worker reports, capped at one report interval, so a stalled worker still reads as an underrun to the budget.

Measured on the GIF folder, 2560×1440 (200 cards), everything cached: all 200 playing at 30 fps (p50), zero dropped frames, clocks at 100%, 9% total CPU, renderer ~990 MB; folder load with one 58 ms long task; scroll p95 21 ms with no long tasks; hover p95 7 ms; blurred and minimized 0% CPU (decoders released). `<video>` on the same screen: 106 playing, the rest held on a frame. Proxy encoding runs two at a time on small machines and up to four on 16-thread ones. Open: a card's first visit still shows a poster until its proxy exists; the canvas shows the proxy's first frame and the hover scale applies to the canvas like any thumbnail.
